# Curated reciter data guide

`data/curated/reciters/` is the manually maintained canonical mapping layer. Each snake_case filename stem is one canonical reciter ID. The Markdown files, not `catalog.json`, are the source of truth.

`data/raw/` contains replaceable provider responses generated by `fetch-reciters`; never hand-edit it. `data/curated/catalog.json` is generated from Markdown by `generate-catalog`; never hand-edit it either.

## File format

```markdown
#name
en:Maher Hamad Al-Muaiqly
ar:ماهر بن حمد المعيقلي

# QFS
{ ...chapter-reciters entry... }

# QFA
{ ...ayah-recitations entry... }

# MP3
{ ...mp3quran reciter entry... }

# EA
"28": { ...everyayah entry... },
```

Rules:

- Start every file with `#name`, followed by `en:` and `ar:` lines. Do not infer missing names. Use the literal `unknown` only when it is an explicit, reviewed unresolved value.
- Keep all four provider headers (`QFS`, `QFA`, `MP3`, and `EA`), leaving a section empty when no binding is curated.
- Preserve raw JSON fields and values verbatim. Apart from the curated-only fields below, a strict audit deep-equals each pasted entry to the current raw entry.
- Multiple entries under one provider tag are permitted. EA entries retain their quoted string-ID fragment shape because the raw catalog is keyed by ID.
- Do not add prose inside a curated file. Keep a blank line between sections.

## Provider domains and raw sources

| Tag | Provider domain | Raw file | Entry identity |
|---|---|---|---|
| QFS | Quran Foundation surah/chapter | `data/raw/quran_foundation/chapter-reciters.json` | integer `id` |
| QFA | Quran Foundation ayah | `data/raw/quran_foundation/ayah-recitations.json` | integer `id` |
| MP3 | mp3quran.net | `data/raw/mp3quran/reciters.json` | integer `id`; each `moshaf` is a recording binding |
| EA | everyayah.com | `data/raw/everyayah/recitations.json` | string-keyed ID fragment |

QFS and QFA are different provider domains and different ID spaces. Never join, deduplicate, or classify entries across tags merely because their IDs or names happen to match.

## Allowed curated-only metadata

Strict audit ignores only these appended fields. Every other raw field must remain exactly as it appears in the provider snapshot.

### QFA

- `riwaya`: required normalized riwayah slug for every QFA entry. Quran Foundation ayah data does not provide the catalog riwayah directly.
- `catalog_style`: required normalized style slug only when raw QFA `style` is `null`; when raw style is present, the generator maps that raw value instead.

These fields are explicit curation, not routine inference. If the value is not known, leave the entry unresolved and let generation report it; do not guess.

### EA

- `style`: required normalized style slug, such as `murattal`, `mujawwad`, `muallim`, or `translation`.
- `riwaya`: required normalized riwayah slug except for `style: "translation"`, which generates under `riwayat.none`.
- `dead`: optional boolean. `true` retains a known unavailable EA source for audit/history but excludes it from the generated catalog.

`unknown` is a valid normalized slug only when it records a deliberate unresolved curation decision. It is not a fallback that the parser or generator supplies automatically.

## Updating after a provider refresh

```bash
fetch-reciters
audit-reciters --strict
```

For each strict-audit result, manually re-copy a changed raw entry, add a missing raw entry to the correct canonical file, or resolve a stale/duplicate/malformed record deliberately. Do not bulk-regenerate curated Markdown and do not use fuzzy matching to merge reciters.

After all curated issues are resolved, generate and verify the derived catalog:

```bash
generate-catalog
generate-catalog --check
```

Generation is offline and deterministic. It parses and builds fully in memory, then atomically replaces `data/curated/catalog.json` only on success. A malformed header/snippet, missing classification, unsupported terminology, or nondeterministic checked-in catalog makes the command fail and preserves the previous catalog. `--check` never writes.

## One-time bootstrap migration

`bootstrap-catalog --json` is report-first, one-time migration tooling, not a curation or refresh command. It compares a legacy catalog against canonical Markdown and reports exact, safe candidate backfills and conflicts. `--apply` may be used only after review and only for unambiguous legacy-backed values. Bootstrap does not authorize fuzzy matches, invented fields, or automatic replacement of the catalog.

Bootstrap accepts only the former `styles -> riwayat` catalog hierarchy. Once `catalog.json` has the generated `riwayat -> styles` hierarchy, bootstrap rejects it; use the normal audit/generate/check workflow instead.

## Adding a provider

1. Add a fetcher under `src/reciter_fetcher/providers/` and register it in `PROVIDERS`.
2. Add a corresponding `SectionSpec` to `AUDIT_SECTIONS` in `src/reciter_fetcher/audit.py`.
3. Add the curated tag to `REQUIRED_SECTIONS` in `src/reciter_fetcher/curated.py`.
4. Map that tag to its public catalog provider key in `_SECTION_PROVIDER` in `src/reciter_fetcher/catalog.py`.
5. Add explicit catalog classification and dispatch for the tag in `build_catalog`; unknown source terminology must produce actionable issues, never guesses.
6. Add the provider tag to `templates/_template.md`.
7. Extend this guide and the README provider table, and add parser, audit, and catalog tests for the new tag.

Keep the package dependency-free and run `python3 -m unittest discover -s tests` after code changes.

## Rules for AI assistants

- Never regenerate, rewrite, or bulk-edit curated reciter Markdown. Propose or apply only the requested manual curation, then run `audit-reciters --strict`.
- Never hand-edit raw provider snapshots or generated `catalog.json`.
- Preserve raw wording, including Arabic, exactly. Do not infer missing identity, names, riwayah, style, capability, or representation.
